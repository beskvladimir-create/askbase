The Askbase row is the same open Qwen2.5-Coder-14B weights plus the application’s prompt, on the same set and through the same interface. It belongs to this site’s held-out set and is not part of the BIRD study published as arXiv:2606.29733.

  • The SQL specialised models come last here. The 65.32 claimed for XiYanSQL-14B becomes 19.3 in English, on a set it had never seen.
  • The headline figure is low on purpose. The set is built from traps. On the questions without a schema trap the leader is right 83.3% of the time.

What this measurement is

The published figures for text-to-SQL models cannot be compared with one another. Each one was produced by the model’s own authors, with their prompt and their way of putting the schema in it, and that difference is larger than the difference between the models. Here every model is measured the same way, and the protocol was published before the run rather than after it.

  • 6models run, 16 runs in all
  • 288questions over six schemas written after the models were trained
  • 2languages, two wordings per question
  • 5points of difference on one model from nothing but how the schema is written into the prompt

The measure is strict: the set of rows a query returns has to match the set of rows the gold query returns. Every interval is a percentile bootstrap over tasks rather than wordings, 2000 resamples, two seeds. Where the seeds disagree, no verdict is given. Every gold query was executed against real data before its question was written down.

What follows from it, and what to install

Among the general purpose models Qwen2.5-Coder-14B is ahead of Qwen2.5-Coder-7B in both languages: 36.8% against 25.9% in English. At 288 tasks the intervals no longer overlap, and this is the difference that the 48 tasks of the first set could not show.

The slowest model is not the strongest. Arctic in Q8 spends 51.33 s at the ninety-fifth percentile and loses to Qwen2.5-Coder-7B, which answers in 9.15 s.

Wording agreement has to be read together with accuracy. XiYanSQL-14B has the highest of all, 91.3% in Russian, and the lowest accuracy. It answers consistently, and consistently wrong. Consistency without correctness is worth nothing.

Where Askbase is in this

There is a row in the table, and it appeared only now. The application’s prompt was tuned on the first held-out set, so its figure there would have been a mark awarded on a textbook it had already read. A second set was written for the decision: 288 tasks over the same six schemas, four wordings each, frozen with a SHA-256 digest on 2 November, before the first request. The run went from 2 to 4 November, once, from committed code. The first set stays labelled as the calibration set, and nothing may be decided on it any more.

The engine went through the same interface as the others, in the same question order and with the same evaluator. The prompt is the only difference. The second arm, with the tables left in creation order, does not ship: the rule was written before the run, the paired interval against the shipping prompt had to exclude zero in both languages, and it came out at -4.34 to 1.04 in English and -1.56 to 3.82 in Russian.

How to read the headline figure

This is not what a plain question gets. The set is built from traps: a column of minor units named as if it were an amount, a status kept as a number, a date split across two columns by a migration. On the tasks without such a trap Askbase is right 83.3% of the time, and where every trap is schema semantics, 57.0%, both on the same strict measure as the headline. The figure is low because the set was written to find the places where a model is confidently wrong, and that is the only kind of figure worth publishing before somebody connects their own database.

Failures are read by hand, and on this set the evaluator was rarely wrong. Twenty random failures from each of the sixteen runs, 320 in all, were read with the gold query and both result sets side by side. 21 of the 320 were false alarms of the evaluator, which is 6.6%, and per run it runs from 0% to 20%. On the first set the same share was 20.8%: there some gold queries returned a column the question had not asked for. Set 2’s gold queries were written to the rule "the answer holds only what was asked", and the share fell threefold. It is in the table, per run.

This is why the application shows the query and the rows rather than one sentence. A wrong answer that announces itself costs a minute. The dangerous queries are the ones that execute and return plausible rows, and no confidence score catches those. A person who can read the query does.

The protocol, frozen before the run

Everything listed here was written down before a single model was measured, and it sits in the repository together with the commit that fixed it. If any of it changes, the run is repeated rather than amended.

  • The same questions for every participant, in the same order, from a deterministic sample.
  • One prompt, greedy decoding, one call, no in-context examples unless that is what is being measured.
  • One context budget and one execution timeout for everyone.
  • Our engine goes through the same interface as the rest, with no privileges.
  • Per-question predictions are published with every published run, the wrong ones included. For set 2 the gold query, the model’s query, the verdict and the hand review of the failures are published for each of the 1152 wordings. The question texts are withheld while the set is live, and the reason is written down in HOLDOUT.md.
  • Intervals by bootstrap over tasks, 2000 resamples, seed 0. A verdict that moves between seeds 0 and 5 is recorded as undetermined.

A held-out set is one set of schemas and one gold query per task, with four wordings of the question written against it: two English and two Russian. That is what makes the gap between languages measurable against the same target, which no published set offers. The Russian wordings were written from the meaning rather than translated from the English, or the measurement would have degenerated into a test of translation quality.

Why a set of our own, when public benchmarks exist. Jin, Choi, Zhu and Kang, writing in PVLDB 19(5), found annotation errors in 52.8% of BIRD Mini-Dev problems and 62.8% of the Spider 2.0-Snow problems with open gold queries. Correcting them moved leading systems by up to 19 points and by as much as nine places, five on average. A score on a public benchmark is a comparison with other papers, not a promise about anyone’s data.

One verdict rule for all of them. Met if the whole 95% interval lies on the right side of the threshold. Not met if the whole interval lies on the other side. Otherwise undetermined, and that is what gets recorded rather than rounded into an answer.

What this page will not do

It will not put a figure from somebody else’s model card beside our measurements as if they were the same thing. Such numbers appear in the text with a link to their source and never in the table above. It will not drop a model over an inconvenient result: the list of participants published is the one above.

Every failure is read by hand before a verdict, at least twenty random ones per run, and classified as a model error or a false alarm of the evaluator. The share of the second kind is published beside the accuracy. This check exists because an evaluator is wrong in exactly the way a benchmark’s annotations are wrong.
