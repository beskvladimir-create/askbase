Which open models are actually good at SQL, measured the same way

Vladimir Beskorovainyi, Enterprise AI Architect & CTO, author of the Amazon bestseller “Enterprise AI: The KATA Way”, founder of Besk Tech (besk.tech)

Published figures for text-to-SQL models cannot be compared with each other. Each comes from its authors, under their own prompt and their own way of showing the schema, and the difference that makes is larger than the difference between the models. This page measures them all one way, and publishes the protocol before the run rather than after.

What that table does not tell you

Nothing in it is comparable. Each number comes from its authors under their own prompt, their own schema format and their own decoding, on a benchmark whose annotations are wrong in half the cases. A five point swing from the schema format alone is larger than the gap between most of these rows. That is the entire reason for the measurement below.

What this says, and what to install

Install Qwen2.5-Coder-14B. It is first on both languages here and it is a general-purpose model, not a text-to-SQL one. Qwen2.5-Coder-7B is half the size and roughly twice as fast, and the difference between them is +2.1 points on English with the interval crossing zero, so on English wordings there is nothing to choose; on Russian the 14B is 9.4 points ahead and the interval touches zero. If the machine is tight or the questions are English, the 7B is a fair trade.

The specialised models lose on an unseen set. XiYanSQL sits third on the published BIRD table above and comes last here, at 24.0% against the 49.0% of a general model of the same size. Both were measured under one protocol, in the same quantisation, on a set neither had seen. Whatever their BIRD figure is measuring, it does not survive contact with six schemas written after the model was trained.

Read the headline figure correctly

49% is not what a straightforward question gets. The set is built out of traps: a column of cents named for the amount, a status held as a number, a date left in two columns by a migration. On the tasks that carry no such trap the same model answers 68.8 correctly, and on the tasks whose only difficulty is of that kind it answers 31.6, both on the same strict measure as the headline figure. The number is low because the set was written to find the places where a model is confidently wrong, which is the only kind of number worth publishing before someone connects their own database.

A fifth of the failures are not failures. The hand review of twenty failures from each run found that the evaluator itself was wrong in 45% of them for the model above, and between 15% and 45% across the twelve runs, mostly by demanding a column the question never asked for. That share is in the table, per run, and the corrected figures are published beside the pre-registered ones as a sensitivity rather than instead of them.

This is why the application shows you the query and the rows rather than a sentence. A wrong answer that announces itself costs a minute. The ones that matter are the queries that run and return plausible rows, and no confidence score catches those. A person who can read the query can.

The protocol, fixed before the run

Everything here was written down before any model was measured, and it is in the repository with the commit that fixed it. If any of it changes, the run is repeated, not edited.

  • The same questions for every participant, in the same order, from a deterministic sample.
  • One prompt, greedy decoding, a single call, no examples in the context, unless the thing being measured is one of those.
  • The same context budget and the same execution timeout for everyone.
  • Our own engine runs through the same interface as everyone else, with no privileges.
  • Per-question predictions are published alongside every run that is published, including the wrong ones. They are in results/, one line per question with the generated query and the gold, together with the hand review of each run and the runs that were withdrawn.
  • Confidence intervals by bootstrap over questions, 2000 resamples, seed 0. A verdict that moves between seeds 0 and 5 is recorded as undetermined.

Our held-out set, set 1frozen 27.10.2026 with a SHA-256 per domain, before any tool saw it. Six domains, eight tasks each. Calibration set: at this size it can fix the open thresholds and measure the gap between languages, and it cannot separate models whose accuracy differs by less than about 28 points. Set 2, at 600 tasks, is the deciding one and is not generated yet. The freeze48 of 600the open thresholds, and the gap between languages

The held-out set is one set of schemas and one gold query per task, with four wordings of the question: two English, two Russian. That is what makes the gap between languages measurable on an identical target, which no published set offers. The Russian wordings are written from the meaning, never translated from the English, or the measurement collapses into a test of translation quality.

Why a set of our own, when public benchmarks exist. A CIDR 2026 study by Jin, Choi, Zhu and Kang found annotation errors in 52.8% of BIRD Mini-Dev problems and 66.1% of the Spider 2.0-Snow problems with open gold queries. Correcting them moved leading systems by up to 19 points and by as much as three places. A score on a public benchmark is a comparison with other papers, not a promise about anyone's data.

One verdict rule for all of them. Met, if the whole 95% interval lies on the right side of the threshold. Not met, if the whole interval lies on the wrong side. Otherwise undetermined, and it is reported as undetermined rather than rounded into an answer.

What this page will not do

It will not quote a figure from someone else's model card next to our own measurements as though they were the same kind of thing. Those numbers appear in prose, with a link to their source, and never in this table. It will not drop a model because the result was inconvenient: the participant list above is the list that gets published.

Every failure is reviewed by hand before a verdict, at least twenty random ones per run, and split into errors of the model and false alarms of the evaluator. The share of false alarms is published next to the accuracy. That check exists because an evaluator can be wrong in exactly the way a benchmark's annotations can.
