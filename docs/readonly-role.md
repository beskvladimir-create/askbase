# Роль только для чтения

Этот текст написан для администратора базы данных. Он отвечает на один вопрос: что именно Askbase будет делать с базой и как ограничить его так, чтобы не полагаться на обещания.

Короткий ответ: создайте отдельную роль, которая умеет только читать, и дайте её Askbase. Всё остальное в приложении это второй и третий рубеж, а первый ваш.

## Что приложение выполняет

Один оператор `SELECT` за запрос. Перед выполнением запрос разбирается, и выполняется он только если прошёл белый список:

- ровно одно выражение, точка с запятой со вторым оператором отклоняется;
- только `SELECT`, допускается ведущий `WITH`;
- никаких `INSERT`, `UPDATE`, `DELETE`, `DROP`, `CREATE`, `ALTER`, `TRUNCATE`, `GRANT`;
- никакого управления транзакциями, `PRAGMA` и служебных команд;
- рекурсивные `WITH` запрещены;
- таблицы и столбцы с указанием таблицы сверяются со слепком схемы, снятым при подключении;
- если в запросе нет `LIMIT`, приложение его добавляет.

Отклонённый запрос показывается пользователю с причиной и не выполняется.

Сверх этого на каждый запрос стоит таймаут и ограничение на число возвращаемых строк.

## Чего приложение не делает

- Не ходит в сеть. Модель лежит файлом на диске, приложение работает с выключенным Wi-Fi.
- Не отправляет телеметрию. Её нет.
- Не хранит пароль в файле настроек. Пароль уходит в Связку ключей macOS.
- Не пишет ваши данные в журнал. В журнал пишется текст запроса, время и число строк.

## Почему одних только правил приложения недостаточно

Потому что это защита одного уровня, а её мало. В работе ICSE 2025 (Pedro и соавторы, «Prompt-to-SQL Injections in LLM-Integrated Web Applications») показано, что на неизменённом каркасе агента внедрённая через текст инструкция получает полный доступ на чтение и запись, и что попытки защититься правкой формулировок оказались крайне хрупкими.

Отдельно: роль только для чтения не спасает от отказа в обслуживании. В отчёте об уязвимости Langchain-Chatchat тяжёлый рекурсивный `WITH` исчерпывал ресурсы при включённом режиме только для чтения. Поэтому рекурсивные выражения у нас запрещены разбором, а не правами.

Отсюда простое правило: права в базе и разбор запроса в приложении решают разные задачи и нужны оба.

## PostgreSQL

Создайте роль, выдайте ей право на чтение нужной схемы и ничего больше. Подставьте свои имена вместо `analytics`, `askbase_ro` и пароля.

```sql
-- 1. Роль только для входа, без наследования лишнего
CREATE ROLE askbase_ro LOGIN PASSWORD 'задайте_свой_пароль';

-- 2. Доступ к базе и схеме, без права создавать объекты
GRANT CONNECT ON DATABASE analytics TO askbase_ro;
REVOKE CREATE ON SCHEMA public FROM askbase_ro;
GRANT USAGE ON SCHEMA public TO askbase_ro;

-- 3. Чтение существующих таблиц
GRANT SELECT ON ALL TABLES IN SCHEMA public TO askbase_ro;

-- 4. Чтение таблиц, которые появятся позже
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO askbase_ro;
```

Ограничьте ресурсы на уровне роли, чтобы тяжёлый запрос не задел остальных:

```sql
-- запрос дольше 30 секунд снимается
ALTER ROLE askbase_ro SET statement_timeout = '30s';
-- простаивающая транзакция не держит блокировки
ALTER ROLE askbase_ro SET idle_in_transaction_session_timeout = '60s';
-- на всякий случай сессия только для чтения
ALTER ROLE askbase_ro SET default_transaction_read_only = on;
```

Если часть столбцов читать нельзя, не выдавайте права на таблицу целиком. Сделайте представление с нужными столбцами и дайте права на него:

```sql
CREATE VIEW clients_safe AS
  SELECT id, region_id, dt_reg FROM clients;   -- без имён и телефонов
GRANT SELECT ON clients_safe TO askbase_ro;
REVOKE SELECT ON clients FROM askbase_ro;
```

Это заодно улучшает ответы: в слепок схемы попадёт только то, что разрешено, и модель не станет строить запросы к закрытым столбцам.

Проверьте, что получилось:

```sql
-- должно вернуть строки
SET ROLE askbase_ro; SELECT count(*) FROM clients_safe;
-- должно завершиться ошибкой прав
SET ROLE askbase_ro; CREATE TABLE t_probe(x int);
RESET ROLE;
```

## MySQL

```sql
CREATE USER 'askbase_ro'@'localhost' IDENTIFIED BY 'задайте_свой_пароль';
GRANT SELECT ON analytics.* TO 'askbase_ro'@'localhost';
FLUSH PRIVILEGES;
```

Ограничение по времени задаётся подсказкой в запросе, а не правом роли, поэтому таймаут здесь обеспечивает приложение. Если версия сервера поддерживает, ограничьте нагрузку на пользователя:

```sql
ALTER USER 'askbase_ro'@'localhost'
  WITH MAX_QUERIES_PER_HOUR 2000 MAX_USER_CONNECTIONS 4;
```

Как и в PostgreSQL, для скрытия отдельных столбцов используйте представления и давайте права на них, а не на исходные таблицы.

## SQLite

Отдельных пользователей в SQLite нет, права задаются файлом. Дайте файлу базы право только на чтение для той учётной записи, под которой работает приложение:

```bash
chmod 444 /путь/к/analytics.sqlite
```

Надёжнее работать с копией, а не с боевым файлом. Копия снимается так, чтобы не поймать базу в середине записи:

```bash
sqlite3 /путь/к/analytics.sqlite ".backup '/путь/к/analytics-ro.sqlite'"
chmod 444 /путь/к/analytics-ro.sqlite
```

## Что проверить перед тем, как пускать в контур

1. Подключите приложение созданной ролью. На экране подключения оно показывает, какие права у роли. Если видите предупреждение о праве на запись, роль создана не так.
2. Выключите Wi-Fi и задайте вопрос. Ответ должен прийти.
3. Откройте журнал запросов и убедитесь, что в нём текст запросов и число строк, а не данные.
4. Попробуйте в базе от этой роли создать таблицу. Должна быть ошибка прав.

## Что мы не можем сделать за вас

Роль только для чтения не ограничивает, какие именно данные видит пользователь. Если человеку нельзя видеть зарплаты, запрет должен быть в правах или в представлении, а не в приложении. Приложение честно покажет всё, к чему у роли есть доступ.
